# Pivex private journal storage: implementation plan, not a migration

## Findings

The deployed website's `web/src/lib/website-auth.ts` authenticates a shared password. Its signed cookie contains version, issue/expiry times, origin audience and a random nonce. It does not contain an authenticated individual user ID or Supabase access token. The nonce is session randomness, **not a person or journal owner**. Challenge labels and browser profiles are not ownership evidence.

The older Streamlit application separately uses Supabase sign-in (`modules/auth.py`) and a client in Streamlit session state (`modules/supabase_client.py`). `modules/data.py` scopes legacy operations by a supplied user ID. Existing SQL, including `supabase/alphaos2_trade_ledger.sql`, models owner IDs and RLS for other ledger records. None establishes a verified Next website identity or authorizes this Pivex dashboard to write those records. Live project settings/policies were not changed or claimed verified. The website's public Supabase configuration placeholders do not prove an authorized authenticated session exists.

Therefore this milestone keeps the documented browser/origin/profile-local storage boundary. Data remains readable to other users of the same browser profile and remains after website logout. It is not encrypted account-scoped cloud storage. Backups and local challenge labels are explicit; no server endpoint or shared database table was added, and no service-role key was read or exposed.

## Proposed implementation stages

1. **Establish website identity.** Add an approved individual sign-in flow, e.g. Supabase Auth with validated server-side sessions and account recovery. Preserve the website gate if needed as an outer gate, but never use it for row ownership. Bind requests to a verified user subject; reject missing/expired/anonymous identities according to product policy. Do not infer identity from user-editable metadata, a challenge label or a client-supplied owner ID.
2. **Create an isolated Pivex schema.** Proposed entities: `pivex_accounts(id, owner_id, schema_version, created_at)`, immutable rule versions, journal records and account/report observations. Separate actual user-reported and advanced observations from hypothetical backtests. Include record schema/model versions and numeric/timestamp constraints. Every child must have an account/owner relationship enforced by a composite foreign key or equivalent invariant, preventing a user from attaching their row to someone else's account.
3. **Authorize at both server and database.** Use a user-scoped client with the validated access token. Enable RLS and restrict policies to the authenticated owner, including SELECT, INSERT, UPDATE and DELETE as appropriate. Ownership predicates use the verified auth subject (`auth.uid()`), with both `USING` and `WITH CHECK` for updates. Restrict exposed schemas/grants explicitly. Never use a service-role client to bypass journal RLS, never accept owner reassignment, and never expose privileged keys through `NEXT_PUBLIC_*`, HTML or logs. Keep privileged archive access independent.
4. **Protect server routes.** Validate identity, same-origin mutations, bounded schema-validated bodies, account ownership and per-account permissions. Derive owner ID server-side, return 401/403 for unauthorized access, avoid distinguishable cross-user record disclosure, and use private/no-store responses. Include optimistic record revisions/ETags and transactionally reject lost updates. Version APIs and backups independently from rule versions.
5. **Idempotent, reviewable migration.** User signs in, explicitly selects/creates their owned account, exports a local backup, then previews records/duplicates/conflicts before confirming a server import. Preserve source/time and never upgrade user-reported data into broker verification. Generate a canonical payload hash and import batch ID; enforce unique `(owner_id, account_id, source_record_id)` keys. Same ID/content is a no-op; differing content is a conflict, not silent overwrite. Use an all-or-nothing transaction and validate returned user-scoped read-back. Retain the browser copy until the user explicitly chooses to remove it after verification. An account label alone never assigns ownership.
6. **Export/retention/recovery.** User-scoped exports include schema versions, provenance and stable IDs. Define retention, account deletion, download auditing, backup restore and session revocation. Test export/import across versions and repeated batches; reject duplicate economics under altered IDs for review where determinable without collapsing legitimate separate trades.

## Release gates before cloud persistence

- Test user A versus user B for every account/journal read, write, update, delete and export, including known foreign UUIDs and child-parent mismatches.
- Test unauthenticated requests, forged/expired credentials, cross-origin mutations, owner reassignment and anonymous identities. A shared-password cookie must fail the per-user route gate.
- Exercise real database RLS: one user's query sees only their rows, updates cannot reparent ownership, missing SELECT/UPDATE policy behavior is understood, and direct Data API access remains protected.
- Confirm no privileged secrets appear in client bundles, errors, redirects, logs or exports. Audit views/functions for RLS bypass, untrusted metadata and privileged execution.
- Test concurrent edits, interrupted/duplicate imports, conflicting revisions, unknown schema versions, backups, rollback and recovery before approving a migration.
- Review production migrations separately; obtain approval before applying them. This document is not an executable migration and changes no infrastructure.

This is a future plan, not evidence that production policies have passed these tests.
